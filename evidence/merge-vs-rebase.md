# مقایسه `git merge` و `git rebase`

دستورهای `git merge` و `git rebase` هر دو برای ترکیب تغییرات Branchها استفاده می‌شوند، اما روش انجام این کار و تأثیر آن‌ها بر تاریخچه Git متفاوت است.

## تفاوت History

دستور `git merge` تاریخچه دو Branch را به یکدیگر متصل می‌کند. در این روش Commitهای قبلی بدون تغییر باقی می‌مانند و SHA آن‌ها عوض نمی‌شود. اگر دو Branch مسیر جداگانه‌ای طی کرده باشند، Git معمولاً یک Merge Commit ایجاد می‌کند تا محل ادغام آن‌ها مشخص باشد. بنابراین تاریخچه واقعی Branchها حفظ می‌شود، اما ممکن است کمی شلوغ‌تر باشد.

دستور `git rebase` Commitهای Branch فعلی را برمی‌دارد و تغییرات آن‌ها را روی آخرین Commit از Branch مقصد دوباره اجرا می‌کند. در نتیجه Commitهای جدیدی با SHAهای جدید ساخته می‌شوند. تاریخچه بعد از Rebase معمولاً خطی و مرتب‌تر است، اما دیگر مسیر واقعی جداشدن و دوباره ادغام‌شدن Branchها به همان شکل قبلی دیده نمی‌شود.

## مزایای Merge

- تاریخچه واقعی توسعه و مسیر Branchها را حفظ می‌کند.
- SHA مربوط به Commitهای قبلی را تغییر نمی‌دهد.
- برای Branchهای مشترک و کار تیمی معمولاً امن‌تر است.

## ریسک‌ها و محدودیت‌های Merge

- Mergeهای زیاد می‌توانند History پروژه را شلوغ کنند.
- اگر Branchها مدت زیادی جدا بمانند، هنگام Merge ممکن است Conflictهای زیادی ایجاد شود.
- حل اشتباه Conflict می‌تواند بخشی از تغییرات یکی از Branchها را از بین ببرد.

## مزایای Rebase

- History پروژه را خطی‌تر و خواناتر می‌کند.
- برای هماهنگ‌کردن یک Feature Branch با آخرین تغییرات Branch اصلی مفید است.
- امکان مرتب‌کردن، ترکیب یا اصلاح Commitهای محلی را قبل از Pull Request فراهم می‌کند.

## ریسک‌ها و محدودیت‌های Rebase

- Rebase تاریخچه را بازنویسی می‌کند و SHA Commitها تغییر می‌کند.
- اگر Branch قبلاً Push شده باشد، ممکن است برای Push مجدد به `--force-with-lease` نیاز باشد.
- هنگام اجرای دوباره Commitها ممکن است Conflict چند بار ظاهر شود و لازم باشد برای هر Commit جداگانه حل شود.

## چه زمانی Merge مناسب‌تر است؟

Merge زمانی مناسب‌تر است که Branch بین چند نفر مشترک باشد یا تغییرات آن قبلاً روی Remote قرار گرفته باشد. همچنین وقتی حفظ مسیر واقعی توسعه، SHA Commitها و نقطه ادغام Pull Request اهمیت دارد، Merge انتخاب مطمئن‌تری است. برای ادغام نهایی Featureها در Branch اصلی نیز معمولاً از Merge استفاده می‌شود.

## چه زمانی Rebase مفید است؟

Rebase بیشتر برای Branchهای شخصی و محلی مناسب است؛ یعنی زمانی که فقط یک نفر روی Branch کار می‌کند و Commitهای آن هنوز مبنای کار دیگران قرار نگرفته‌اند. می‌توان پیش از ایجاد Pull Request، Branch را روی آخرین نسخه Branch اصلی Rebase کرد تا History مرتب‌تر شود. Interactive Rebase نیز برای ترکیب Commitهای کوچک یا اصلاح پیام Commitها مفید است.

## چرا روی Branch مشترک باید در Rebase احتیاط کرد؟

Rebase Commitهای قبلی را نگه نمی‌دارد، بلکه تغییرات آن‌ها را به‌صورت Commitهای جدید بازسازی می‌کند. به همین دلیل SHA Commitها تغییر می‌کند. اگر توسعه‌دهنده دیگری Branch مشترک را دریافت کرده و کار خود را بر پایه Commitهای قبلی ادامه داده باشد، بعد از Rebase تاریخچه سیستم او با تاریخچه جدید Remote متفاوت خواهد شد.

در این شرایط ممکن است Branchها از یکدیگر Diverge شوند، Commitهای تکراری ایجاد شود یا Push و Pull با Conflict مواجه شود. همچنین Force Push اشتباه می‌تواند تغییرات دیگران را از Remote حذف کند. استفاده از `git push --force-with-lease` از `--force` ایمن‌تر است، اما خطر بازنویسی History مشترک را کاملاً از بین نمی‌برد.

بنابراین بهتر است Commitهایی که دیگران دریافت کرده‌اند بدون هماهنگی Rebase نشوند. Rebase برای مرتب‌کردن Branch شخصی مناسب است، اما Merge برای ادغام Branchهای مشترک معمولاً انتخاب امن‌تری محسوب می‌شود.

## نتیجه‌گیری

`merge` تاریخچه موجود را حفظ و Branchها را به یکدیگر متصل می‌کند؛ در مقابل، `rebase` Commitها را روی یک Base جدید دوباره ایجاد می‌کند و History را خطی‌تر می‌سازد. انتخاب بین آن‌ها به مشترک یا شخصی بودن Branch، سیاست تیم و اهمیت حفظ تاریخچه واقعی بستگی دارد.
